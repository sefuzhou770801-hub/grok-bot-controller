# 设备唤醒衔接协议草案（2026-08-25）

本草案只描述设备经现有 WebSocket 通道把唤醒事件通知网关的约定。不改网关仓库代码。对照代码：

- 设备：`components/conversation/xiaozhi_client.cpp`（当前只发 `listen/start`，不发 `detect`）
- 上游探针：`main/asr_probe.cpp`（命中后本地说「はい」，不通知网关）
- 网关已有路径：`gateway/stackchan_mcp/esp32_client.py` 的 `_observe_device_state`，以及 `wake_gate.py` / `gemini_voice_proxy.py`
- xiaozhi 方言原文：[firmware/docs/websocket.md](https://github.com/78/xiaozhi-esp32) 与主仓 `firmware/main/protocols/protocol.cc` 的 `SendWakeWordDetected`

原则：复用已有 `type=listen, state=detect` 消息，不造新类型。旧网关看见这条消息已经会走 `on_wake_detected`。新增字段一律可选，缺省时行为与今天一致。

---

## 1. 消息字段

### 1.1 设备 → 网关：唤醒检测（必选）

与 xiaozhi `Protocol::SendWakeWordDetected` 同形：

```json
{
  "session_id": "<hello 之后的会话 id，可空则省略该键>",
  "type": "listen",
  "state": "detect",
  "text": "你好小克"
}
```

| 字段 | 必选 | 取值 | 说明 |
|---|---|---|---|
| `type` | 是 | `listen` | 现有控制面 |
| `state` | 是 | `detect` | 本地唤醒已触发 |
| `text` | 是 | 唤醒词原文 | 中文产品用 `你好小克`。日语探针阶段允许 `こんにちはESP`。网关用原文做日志，不做分词 |
| `session_id` | 否 | hello 返回的 id | 有则带，与现有 `listen/start` 一致 |

不新增 `type`。不把唤醒词塞进 `abort.reason` 当主通知（`abort` 仍只用于打断 TTS）。

### 1.2 设备 → 网关：开始上行（已有，保持）

当前 `XiaoZhiClient::send_listen_start()` 在 hello 之后发一次：

```json
{
  "session_id": "<id>",
  "type": "listen",
  "state": "start",
  "mode": "auto"
}
```

`mode=auto` 表示服务端 VAD。Gemini 路径下这条对模型无意义，但网关 `_observe_device_state` 会把它映射成 `listening`。ASR 衔接后这条仍在会话建立时发一次，不在每次唤醒时重发。

### 1.3 设备 → 网关：停止上行（可选，默认不发）

当前固件注释写明：`mode=auto` 下中途 `listen/stop` 会被云端当成 barge-in 并打断 TTS，所以现在永不发 stop。

Gemini 路径里，网关 `gemini_voice_proxy.send_device_json` 对 `listen/stop` 会调用 `send_audio_stream_end()`，用来结束用户这一轮。

本草案：设备默认仍不发 `stop`。聆听窗关闭由网关 `WakeGate` 的静音超时与最长窗负责。若后段确认设备要主动结束一轮，再加：

```json
{"session_id":"<id>","type":"listen","state":"stop"}
```

旧网关已能解析，不算新类型。

### 1.4 设备 → 网关：打断（已有）

```json
{"session_id":"<id>","type":"abort","reason":"wake_word_detected"}
```

仅当扬声器正在播放 TTS、用户又说了唤醒词（或设备判定要打断）时发送。唤醒本身不靠这条通知网关。

### 1.5 可选扩展字段（默认不加）

若后段必须区分「设备端命中」和「网关 sherpa 命中」，只允许在 `listen/detect` 上增加可选键：

```json
{
  "type": "listen",
  "state": "detect",
  "text": "你好小克",
  "source": "device"
}
```

| 可选键 | 缺省 | 兼容 |
|---|---|---|
| `source` | 视为 `device` | 旧网关忽略未知键，JSON 解析不失败 |
| `confidence` | 不出现 | 调试用，产品路径不依赖 |

禁止把这些键放到新的 `type=wake` 上。旧网关只认 `type=listen`。

### 1.6 网关 → 设备

本草案不要求网关对 `detect` 回 ACK。设备不能靠应答判断网关是否打开聆听窗。失败回退见第 4 节。

网关现有下行仍可用：`tts/start`、`tts/stop`、表情与 LED MCP/JSON。它们表示「网关确实在动」，可作间接存活信号，但不是协议必选握手。

## 2. 时序

```
设备 WakeNet/MultiNet 命中
    │
    ├─ 本地反馈（短、不占死麦克风）
    │     表情 Happy / 底灯青 / 可选极短提示音
    │     禁止再走 asr_probe 里 say_kana("はい") 那种整句 TTS：
    │     CoreS3 麦克风与扬声器共用 I2S，长回复会丢掉唤醒后第一句
    │
    ├─ WebSocket 文本：listen/detect  {text: "你好小克"}
    │
    ├─ 网关 _observe_device_state
    │     已有：on_wake_detected → 抬头 + 蓝灯（gateway._run_wake_response）
    │     需要补的语义（本草案要求，尚未改代码）：
    │       把这次 detect 视为 WakeGate 命中，状态切到 LISTENING，
    │       放出 preroll，开始把后续 PCM 送给 Gemini
    │
    ├─ 网关开聆听窗
    │     idle_s = 30（STACKCHAN_WAKE_IDLE_S）
    │     max_listening_s = 45（STACKCHAN_WAKE_MAX_LISTENING_S）
    │     preroll_s = 2
    │     聆听青灯 (0,180,180)
    │
    ├─ 音频上行边界
    │     起点：detect 到达时刻（含 preroll 里唤醒词尾音）
    │     正常终点：网关判定静音 ≥ idle_s，或达到 max_listening_s
    │     讲话期间 TTS 活跃则窗口锚点后移（现有 wake_gate._track_tts_activity）
    │     设备继续按现有逻辑推送 Opus 二进制帧，不因 detect 改编码
    │
    └─ 窗关闭
          网关停止向 Gemini 转发 PCM
          灯权回到 DORMANT（无 TTS 时熄状态灯）
          设备端回到只听唤醒，不发 stop
```

hello 之后那一次 `listen/start mode=auto` 只建立会话，不打开产品意义上的「聆听窗」。产品聆听窗只由 `detect` 或网关侧 sherpa 命中打开。

## 3. 网关侧 KWS 旁路条件

现有 `WakeGate.process()`：

- `available == False`（`STACKCHAN_WAKE_WORD=0` 或 sherpa 加载失败）→ `bypassed=True`，每一帧 PCM 直通。
- `available == True` 且状态 `DORMANT` → 只在 sherpa 命中后打开窗口。

设备端唤醒接入后，旁路规则如下。

| 条件 | 网关 KWS | 聆听窗 |
|---|---|---|
| 收到 `listen/detect` | 本轮不要求 sherpa 再命中一次 | 立即打开，等价 `woke=True` |
| `STACKCHAN_WAKE_WORD=0` | 整段直通，与今天相同 | 不存在闸门 |
| sherpa 不可用（`WakeWordUnavailable`） | 直通 | 与今天相同 |
| 未收到 detect，sherpa 仍可用 | 继续在 PCM 上跑「你好小克」 | 网关自身命中也可打开窗口 |
| 同一句既有 detect 又有 sherpa 命中 | 先到者打开，1500 ms 内去抖（与 `asr_probe` 去抖对齐） | 只开一次 |

双路径并存的原因：旧网关还不把 `detect` 映射到 `WakeGate` 时，设备端 ASR 只提供本地表情，真正开窗仍靠 sherpa。新网关把 `detect` 当开窗信号后，sherpa 降为后背，避免设备已唤醒还要用户再说一遍。

不在设备上实现「检测到就停止推 PCM」。PCM 一直推，闸门在网关。这样旧网关行为不变。

---

## 4. 网关未响应时的设备回退

设备无法从协议上确认网关是否打开了聆听窗。回退只依据本地可观察量。

| 现象 | 设备行为 | 时限 |
|---|---|---|
| WebSocket 未连接 | 只做本地反馈，不发 detect，保持听唤醒 | 立即 |
| 已连接，detect 发送失败（`SendFailed` / 超时 3 s） | 记日志，本地反馈仍做；下一轮唤醒再发 | 发送超时沿用现有 3 s |
| detect 已发出，之后 2 s 内没有任何下行（无 tts、无 LED JSON、无表情） | 视为网关没把这次唤醒当一回事。不重发 detect（避免双开窗）。本地保持听唤醒。用户需要再说一次或靠网关 sherpa | 2 s |
| 网关在播 TTS 时设备再次命中 | 发 `abort` `reason=wake_word_detected`，再发 `listen/detect` | 去抖 1500 ms |
| 本地 AFE 初始化失败（`esp_srmodel_init` 空分区） | 不进入 ASR 循环，会话保持普通 conversation。唤醒完全交给网关 sherpa | 启动时一次 |

本地反馈硬约束：

- 可以改表情、改灯、短蜂鸣。
- 不要在命中后立刻用 I2S 播放整句「在」或「はい」。现有 `asr_probe` 的 `say_kana("はい")` 与麦克风互斥，会吃掉唤醒后第一句，产品路径必须拿掉或改到「网关已开窗且用户沉默」之后。
- 气球文字可用「在」或「你好」，时长不超过 1.8 s，与现有 `set_balloon_text(..., 1800)` 同级。

## 5. 与旧网关的兼容

旧网关已经：

1. 解析 `type=listen, state=detect`，调用 `on_wake_detected`（抬头、蓝灯）。
2. 忽略未知 JSON 键。
3. 在 PCM 上跑 sherpa「你好小克」。

因此设备先发 `listen/detect` 不会打坏旧网关。代价是旧网关不会仅凭 detect 打开 `WakeGate`，用户仍要靠 sherpa 或 `STACKCHAN_WAKE_WORD=0`。这是可接受的过渡。

新网关（后段，本任务不做）只需在 `gemini_voice_proxy.send_device_json` 或 `WakeGate` 入口增加：

```
if type==listen and state==detect: gate 视为命中并开窗
```

不必改消息形态。
